# 索引对 WHERE 和 ORDER BY 的优化效果详解

## 1. **索引的有效使用场景**

### 1.1 **WHERE 子句中的索引使用**

#### ✅ **等值查询（最有效）**

```sql
-- 单列索引
CREATE INDEX idx_users_email ON users(email);

SELECT * FROM users WHERE email = 'test@example.com';
-- 使用索引：idx_users_email

-- 复合索引
CREATE INDEX idx_products_category_status ON products(category_id, status);

SELECT * FROM products
WHERE category_id = 3 AND status = 'active';
-- 使用索引：idx_products_category_status（最左前缀匹配）
```

#### ✅ **范围查询**

```sql
-- 单列范围查询
CREATE INDEX idx_products_price ON products(price);

SELECT * FROM products WHERE price > 100 AND price < 1000;
-- 使用索引：idx_products_price

-- 复合索引中的范围查询
CREATE INDEX idx_orders_user_date ON orders(user_id, order_date);

SELECT * FROM orders
WHERE user_id = 123
  AND order_date > '2024-01-01';
-- 使用索引：idx_orders_user_date
```

#### ✅ **IN 查询**

```sql
CREATE INDEX idx_products_category ON products(category_id);

SELECT * FROM products WHERE category_id IN (1, 3, 5);
-- 使用索引：idx_products_category
```

#### ❌ **索引失效的情况**

```sql
-- 1. 在索引列上使用函数
SELECT * FROM users WHERE UPPER(email) = 'TEST@EXAMPLE.COM';
-- 索引失效：需要在 email 列上创建函数索引

-- 2. 在索引列上使用计算
SELECT * FROM products WHERE price * 1.1 > 100;
-- 索引失效：应该改为 WHERE price > 100 / 1.1

-- 3. LIKE 查询以通配符开头
SELECT * FROM users WHERE name LIKE '%张%';
-- 索引失效（全表扫描）
SELECT * FROM users WHERE name LIKE '张%';
-- 索引有效（前缀匹配）

-- 4. OR 条件（除非所有列都有索引）
SELECT * FROM products
WHERE category_id = 1 OR price > 100;
-- 如果只有 category_id 有索引，可能失效

-- 5. 数据类型不匹配
CREATE INDEX idx_users_phone ON users(phone);  -- phone 是 varchar

SELECT * FROM users WHERE phone = 13800138000;  -- 字符串与数字比较
-- 索引失效：应该用 WHERE phone = '13800138000'
```

### 1.2 **ORDER BY 子句中的索引使用**

#### ✅ **排序查询（最有效情况）**

```sql
-- 单列排序
CREATE INDEX idx_users_created_at ON users(created_at);

SELECT * FROM users ORDER BY created_at DESC;
-- 使用索引：idx_users_created_at（避免文件排序）

-- 复合索引排序
CREATE INDEX idx_products_category_price ON products(category_id, price);

SELECT * FROM products
WHERE category_id = 3
ORDER BY price;
-- 使用索引：idx_products_category_price
```

#### ✅ **多列排序**

```sql
-- 复合索引排序顺序必须匹配 ORDER BY 顺序
CREATE INDEX idx_products_multi_sort ON products(category_id, price DESC, sales_count);

-- ✅ 有效：顺序一致
SELECT * FROM products
WHERE category_id = 3
ORDER BY price DESC, sales_count;

-- ❌ 无效：顺序不一致
SELECT * FROM products
WHERE category_id = 3
ORDER BY sales_count, price DESC;  -- 需要文件排序
```

#### ❌ **ORDER BY 索引失效的情况**

```sql
-- 1. ORDER BY 多列方向不一致
CREATE INDEX idx_a_b ON table1(a ASC, b ASC);

SELECT * FROM table1 ORDER BY a ASC, b DESC;
-- 索引部分有效（只用到 a 列）

-- 2. ORDER BY 包含不在索引中的列
CREATE INDEX idx_category ON products(category_id);

SELECT * FROM products ORDER BY category_id, price;
-- 需要文件排序（price 不在索引中）

-- 3. 同时使用 WHERE 和 ORDER BY，但索引不匹配
CREATE INDEX idx_status_price ON products(status, price);

SELECT * FROM products
WHERE category_id = 3  -- category_id 不在索引最左
ORDER BY price;
-- 需要文件排序

-- 4. 使用表达式排序
SELECT * FROM products ORDER BY price * quantity;
-- 索引失效
```

## 2. **WHERE + ORDER BY 联合优化**

### 2.1 **最佳实践：复合索引设计**

```sql
-- 查询模式：WHERE 过滤 + ORDER BY 排序
SELECT * FROM orders
WHERE user_id = 123
  AND status = 'completed'
ORDER BY created_at DESC;

-- 最佳索引设计：
CREATE INDEX idx_orders_user_status_created ON orders(
    user_id,       -- 等值查询（高选择性）
    status,        -- 等值查询
    created_at DESC -- 排序字段
);

-- 索引使用：完全覆盖 WHERE 和 ORDER BY
```

### 2.2 **索引列顺序原则**

```sql
-- 原则：等值列在前，范围列在中，排序列在后

-- 查询示例：
SELECT * FROM logs
WHERE app_id = 'web'           -- 等值
  AND log_level = 'ERROR'      -- 等值
  AND created_at >= '2024-01-01'  -- 范围
ORDER BY created_at DESC;      -- 排序

-- 最佳索引：
CREATE INDEX idx_logs_optimized ON logs(
    app_id,        -- 等值（高选择性）
    log_level,     -- 等值（中等选择性）
    created_at     -- 范围 + 排序
);

-- 注意：范围查询后的列无法使用索引
-- ❌ 错误示例：
CREATE INDEX idx_wrong_order ON logs(
    app_id,
    created_at,    -- 范围列在等值列前
    log_level      -- 这个列无法使用索引
);
```

## 3. **具体场景分析**

### 场景 1：电商商品搜索

```sql
-- 查询：按分类、价格范围筛选，按销量排序
SELECT * FROM products
WHERE category_id = 3
  AND price BETWEEN 100 AND 1000
  AND status = 'active'
ORDER BY sales_count DESC
LIMIT 0, 20;

-- 索引方案1：覆盖所有条件
CREATE INDEX idx_products_full_cover ON products(
    category_id,      -- 等值
    status,          -- 等值
    price,           -- 范围
    sales_count DESC -- 排序
);

-- 索引方案2：如果 price 范围查询选择性差
CREATE INDEX idx_products_better ON products(
    category_id,      -- 等值
    status,          -- 等值
    sales_count DESC -- 排序在前，price 过滤在后
);

-- 执行计划会选择更好的索引
```

### 场景 2：用户行为日志

```sql
-- 查询：按用户和时间范围筛选，按时间倒序
SELECT * FROM user_actions
WHERE user_id = 456
  AND action_type = 'login'
  AND action_time BETWEEN '2024-01-01' AND '2024-01-31'
ORDER BY action_time DESC;

-- 最佳索引：
CREATE INDEX idx_user_actions_query ON user_actions(
    user_id,        -- 高选择性等值
    action_type,    -- 等值
    action_time     -- 范围 + 排序（同列）
);

-- 注意：DESC 排序需要数据库支持倒序索引
CREATE INDEX idx_user_actions_desc ON user_actions(
    user_id,
    action_type,
    action_time DESC  -- MySQL 8.0+ 支持
);
```

### 场景 3：消息分页

```sql
-- 查询：按接收者、状态筛选，按时间分页
SELECT * FROM messages
WHERE receiver_id = 789
  AND status IN ('unread', 'read')
ORDER BY sent_time DESC
LIMIT 100, 20;

-- 索引设计：
CREATE INDEX idx_messages_receiver_time ON messages(
    receiver_id,    -- 等值
    sent_time DESC  -- 排序
);

-- 如果需要覆盖 status 条件
CREATE INDEX idx_messages_covering ON messages(
    receiver_id,
    sent_time DESC
) INCLUDE (status, content, sender_id);  -- PostgreSQL/SQL Server
```

## 4. **索引失效的边界条件**

### 4.1 **复合索引的最左前缀原则**

```sql
CREATE INDEX idx_a_b_c ON table1(a, b, c);

-- ✅ 有效：使用索引
SELECT * FROM table1 WHERE a = 1;
SELECT * FROM table1 WHERE a = 1 AND b = 2;
SELECT * FROM table1 WHERE a = 1 AND b = 2 AND c = 3;
SELECT * FROM table1 WHERE a = 1 ORDER BY b, c;

-- ⚠️ 部分有效：使用部分索引
SELECT * FROM table1 WHERE a = 1 AND c = 3;  -- 只用到 a 列
SELECT * FROM table1 WHERE b = 2 AND c = 3;  -- 全表扫描（没有 a）
SELECT * FROM table1 ORDER BY a, b;         -- 用到索引排序
SELECT * FROM table1 ORDER BY b;           -- 文件排序（没有 a）
```

### 4.2 **范围查询的边界**

```sql
CREATE INDEX idx_price_stock ON products(price, stock);

-- ✅ 有效：范围查询在最后一列
SELECT * FROM products
WHERE price > 100
ORDER BY price, stock;

-- ⚠️ 部分有效：范围查询在中间列
SELECT * FROM products
WHERE price > 100 AND stock = 50;
-- 只用到 price 索引，stock 需要回表过滤

-- ❌ 无效：跳过等值列
SELECT * FROM products
WHERE stock > 50;  -- 没有 price 条件
```

## 6. **实际优化建议**

### 6.1 **索引设计检查清单**

```sql
-- 1. 识别高频查询
SHOW GLOBAL STATUS LIKE 'Com_select%';

-- 2. 分析慢查询
-- MySQL
SELECT * FROM mysql.slow_log
ORDER BY start_time DESC
LIMIT 10;

-- 3. 使用执行计划
EXPLAIN FORMAT=JSON
SELECT * FROM products
WHERE category_id = 3
ORDER BY price DESC;

-- 4. 检查索引使用率
-- MySQL
SELECT
    object_schema,
    object_name,
    index_name,
    COUNT_READ,
    COUNT_FETCH
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
ORDER BY COUNT_READ DESC;
```

### 6.2 **创建合适的索引**

```sql
-- 综合示例：用户订单查询
-- 查询1：用户订单列表
SELECT * FROM orders
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT ?;

-- 查询2：用户特定状态的订单
SELECT * FROM orders
WHERE user_id = ?
  AND status = ?
ORDER BY created_at DESC;

-- 查询3：按时间范围查询
SELECT * FROM orders
WHERE created_at BETWEEN ? AND ?
ORDER BY created_at DESC;

-- 最佳索引策略：
-- 1. 主索引（最常用查询）
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);

-- 2. 辅助索引（特定场景）
CREATE INDEX idx_orders_user_status_created ON orders(user_id, status, created_at DESC);

-- 3. 范围查询索引
CREATE INDEX idx_orders_created ON orders(created_at DESC);
```

### 6.3 **维护和监控**

```sql
-- 1. 定期重建碎片化索引
-- MySQL
ALTER TABLE orders ENGINE=InnoDB;
ANALYZE TABLE orders;

-- 2. 监控索引使用
SELECT
    table_name,
    index_name,
    rows_read,
    rows_inserted,
    rows_updated,
    rows_deleted
FROM sys.schema_index_statistics
WHERE table_schema = DATABASE();

-- 3. 删除无用索引
SELECT
    t.TABLE_NAME,
    s.INDEX_NAME,
    s.COLUMN_NAME,
    s.SEQ_IN_INDEX,
    s2.NON_UNIQUE,
    s2.INDEX_TYPE,
    STATISTICS.CARDINALITY
FROM INFORMATION_SCHEMA.STATISTICS s
JOIN INFORMATION_SCHEMA.TABLES t
  ON t.TABLE_SCHEMA = s.TABLE_SCHEMA
 AND t.TABLE_NAME = s.TABLE_NAME
LEFT JOIN INFORMATION_SCHEMA.STATISTICS s2
  ON s2.TABLE_SCHEMA = s.TABLE_SCHEMA
 AND s2.TABLE_NAME = s.TABLE_NAME
 AND s2.INDEX_NAME = s.INDEX_NAME
WHERE t.TABLE_SCHEMA = DATABASE()
  AND t.TABLE_NAME = 'orders'
ORDER BY s.TABLE_NAME, s.INDEX_NAME, s.SEQ_IN_INDEX;
```

## 7. **常见问题解决方案**

### 问题1：WHERE 和 ORDER BY 冲突

```sql
-- 查询：按时间范围过滤，按其他字段排序
SELECT * FROM logs
WHERE created_at > '2024-01-01'
ORDER BY user_id;  -- 与 WHERE 条件不同列

-- 解决方案1：创建复合索引（如果 user_id 选择性高）
CREATE INDEX idx_logs_user_created ON logs(user_id, created_at);

-- 解决方案2：使用延迟关联
SELECT logs.*
FROM logs
JOIN (
    SELECT id
    FROM logs
    WHERE created_at > '2024-01-01'
    ORDER BY user_id
    LIMIT 1000
) tmp ON logs.id = tmp.id;
```

### 问题2：多个排序方向

```sql
-- 查询：多列不同方向排序
SELECT * FROM products
ORDER BY price ASC, sales_count DESC;

-- 解决方案：创建匹配的索引
CREATE INDEX idx_products_price_asc_sales_desc ON products(
    price ASC,
    sales_count DESC
);  -- MySQL 8.0+ 支持

-- 或使用函数索引（PostgreSQL）
CREATE INDEX idx_products_sort ON products(price, (-sales_count));
```

### 问题3：分页性能差

```sql
-- 深度分页问题
SELECT * FROM orders
ORDER BY id
LIMIT 1000000, 20;

-- 解决方案：基于主键的分页
SELECT * FROM orders
WHERE id > 1000000  -- 上一页最后一条的ID
ORDER BY id
LIMIT 20;

-- 需要索引：PRIMARY KEY (id)
```

## **总结表格：索引有效性**

| 查询类型                        | 索引是否有效 | 优化建议                 |
| ------------------------------- | ------------ | ------------------------ |
| **WHERE column = value**        | ✅ 有效      | 单列索引或复合索引最左列 |
| **WHERE column > value**        | ✅ 有效      | 范围查询索引             |
| **WHERE column LIKE 'prefix%'** | ✅ 有效      | 前缀索引                 |
| **WHERE column LIKE '%suffix'** | ❌ 无效      | 全文索引或反向存储       |
| **WHERE func(column) = value**  | ❌ 无效      | 函数索引或冗余列         |
| **ORDER BY column**             | ✅ 有效      | 排序字段建索引           |
| **ORDER BY col1, col2**         | ✅ 有效      | 复合索引，顺序一致       |
| **WHERE + ORDER BY**            | ⚠️ 部分      | 复合索引（等值列在前）   |
| **GROUP BY column**             | ✅ 有效      | 分组字段建索引           |
| **JOIN ON column**              | ✅ 有效      | 外键索引                 |

## **黄金法则**

1. **最左前缀原则**：复合索引从最左列开始使用
2. **等值在前，范围在后**：WHERE 中等值条件放索引前面
3. **排序匹配原则**：ORDER BY 顺序与索引顺序一致
4. **覆盖索引优先**：SELECT 的列尽量包含在索引中
5. **高选择性优先**：选择性高的列放索引前面
6. **避免索引列计算**：不要在索引列上使用函数或计算

**记忆口诀：**

> **WHERE 等值最左先，范围查询放后面。**  
> **ORDER BY 顺序配，索引性能翻倍现。**  
> **最左前缀要牢记，跳过列后全失效。**  
> **覆盖索引是法宝，回表操作尽量少。**
