**完全正确！** 如何设计测试——选择单元测试还是集成测试——确实是整个测试策略的**核心关键**。这直接影响到：

- 测试的执行速度
- 代码的维护成本
- Bug 发现的效率
- 开发团队的信心

## 一、测试设计决策树

```
开始测试某个功能
    ↓
是否涉及基础设施（数据库/文件系统/网络）？
    ↓
    ├─ 否 → 【单元测试】✅
    │        测试业务逻辑、算法、计算、验证规则
    │
    └─ 是 → 这个基础设施操作是否为核心流程？
            ↓
            ├─ 是（如：用户注册、支付流程）→ 【集成测试】✅
            │         测试完整的端到端流程
            │         只测试最重要的1-2个场景
            │
            └─ 否（如：普通数据查询）→ 【单元测试】✅
                      使用 Mock 模拟基础设施
                      测试业务逻辑
```

## 二、实际案例对比

### 案例1：用户登录功能

```csharp
public class LoginService
{
    private readonly IUserRepository _userRepo;
    private readonly IPasswordHasher _passwordHasher;
    private readonly ITokenGenerator _tokenGenerator;

    public async Task<LoginResult> Login(string email, string password)
    {
        // 1. 验证输入（业务逻辑）
        if (string.IsNullOrEmpty(email) || string.IsNullOrEmpty(password))
            return LoginResult.InvalidInput;

        // 2. 查找用户（基础设施）
        var user = await _userRepo.GetByEmail(email);
        if (user == null)
            return LoginResult.UserNotFound;

        // 3. 验证密码（业务逻辑）
        if (!_passwordHasher.Verify(password, user.PasswordHash))
            return LoginResult.InvalidPassword;

        // 4. 生成Token（业务逻辑+基础设施）
        var token = _tokenGenerator.Generate(user);

        return LoginResult.Success(token);
    }
}
```

### 案例2：订单计算功能

```csharp
public class OrderCalculator
{
    public decimal CalculateTotal(Order order, IEnumerable<Discount> discounts)
    {
        // 纯业务逻辑：没有外部依赖
        decimal subtotal = order.Items.Sum(i => i.Price * i.Quantity);

        decimal discountAmount = discounts.Sum(d => d.Calculate(subtotal));

        decimal tax = subtotal * 0.1m;

        return subtotal - discountAmount + tax;
    }
}
```

```csharp
        Assert.Equal(100m, result);
    }
```

## 三、测试设计原则

### 1. 测试金字塔

```
        /\
       /  \      ← 集成测试（少量）
      /    \        - 关键业务流程
     /------\       - 端到端场景
    /        \      - 每个功能1-2个测试
   /__________\
  /            \   ← 单元测试（大量）
 /______________\     - 业务逻辑
                      - 边界条件
                      - 异常情况
                      - 每个类10+个测试
```

### 2. 决策矩阵

| 场景             | 测试类型 | 原因                        | 示例                   |
| ---------------- | -------- | --------------------------- | ---------------------- |
| **计算逻辑**     | 单元测试 | 纯算法，无外部依赖          | 折扣计算、税费计算     |
| **输入验证**     | 单元测试 | 业务规则，不依赖基础设施    | 邮箱格式验证、必填字段 |
| **数据库查询**   | 单元测试 | 使用 Mock，测试业务逻辑     | 根据条件筛选数据       |
| **数据库写入**   | 集成测试 | 需要验证真实写入，但只测1次 | 创建用户、更新订单     |
| **文件操作**     | 集成测试 | 需要验证真实文件系统        | 上传文件、导出报表     |
| **外部API调用**  | 集成测试 | 需要验证真实调用            | 支付接口、短信发送     |
| **完整业务流程** | 集成测试 | 关键路径，端到端验证        | 用户注册、下单支付     |

### 3. 实战决策示例

```csharp
// 场景：用户创建订单
public class OrderService
{
    private readonly IOrderRepository _orderRepo;
    private readonly IInventoryService _inventory;
    private readonly IPaymentService _payment;

    public async Task<OrderResult> CreateOrder(OrderDto dto)
    {
        // 1. 验证库存（业务逻辑）
        if (!await _inventory.CheckStock(dto.ProductId, dto.Quantity))
            return OrderResult.OutOfStock;

        // 2. 计算价格（业务逻辑）
        var total = CalculatePrice(dto);

        // 3. 处理支付（基础设施）
        var paymentResult = await _payment.Charge(dto.PaymentMethod, total);
        if (!paymentResult.Success)
            return OrderResult.PaymentFailed;

        // 4. 保存订单（基础设施）
        var order = new Order { ProductId = dto.ProductId, Quantity = dto.Quantity, Total = total };
        await _orderRepo.Save(order);

        // 5. 扣减库存（基础设施）
        await _inventory.DeductStock(dto.ProductId, dto.Quantity);

        return OrderResult.Success(order);
    }
}
```

## 四、常见错误模式

### ❌ 错误1：过度使用集成测试

```csharp
// 错误：为每个业务场景都写集成测试

public async Task CreateOrder_WithDiscount_IntegrationTest() { }
[Fact]
public async Task CreateOrder_WithCoupon_IntegrationTest() { }
[Fact]
public async Task CreateOrder_WithMultipleItems_IntegrationTest() { }
[Fact]

// 问题：运行慢、维护难、测试金字塔倒置
```

### ✅ 正确做法

```csharp

// 多个单元测试（业务逻辑）

public void CalculatePrice_WithCoupon_ReturnsCorrectPrice() { }
[Fact]

```


## 五、测试设计清单

在设计测试时，问自己这些问题：

- [ ] 这个测试主要验证什么？**业务逻辑**还是**组件集成**？
- [ ] 能否用 **Mock 模拟外部依赖**？→ 如果能，用单元测试
- [ ] 是否涉及**数据库写入**的真实验证？→ 考虑集成测试
- [ ] 这是**关键业务流程**吗？→ 考虑1-2个集成测试
- [ ] 测试执行**速度快**吗？→ 单元测试应该 < 100ms
- [ ] 测试是否**可重复**？→ 每次运行结果应该一致
- [ ] 测试是否**独立**？→ 不依赖其他测试的执行顺序

## 总结

**测试设计的核心是找到平衡点**：

1. **80% 单元测试** - 快速、稳定、细粒度
2. **15% 集成测试** - 验证关键路径和基础设施
3. **5% 端到端测试** - 验证最关键的用户场景

记住：

- 能单元测试的绝不集成测试
- 能用 Mock 的绝不连真实数据库
- 集成测试只测试"不得不测"的场景

这样设计出来的测试套件才能**快速反馈、易于维护、真实有效**。
