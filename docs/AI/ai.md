## 🎯 四者定位速览

| 机制          | 一句话定义 | 核心特点                 | 激活方式             |
| :------------ | :--------- | :----------------------- | :------------------- |
| **Rules**     | 行为准则   | 持久性约束，规范 AI 行为 | 自动生效（开关控制） |
| **Skills**    | 专家知识包 | 模块化指令，特定领域深度 | 按需触发（描述匹配） |
| **Workflows** | 任务脚本   | 可重复的多步骤流程       | 手动调用（斜杠命令） |
| **Hooks**     | 自动化钩子 | 事件驱动的自动化操作     | 自动触发（事件监听） |

---

## 📊 详细对比矩阵

### 1️⃣ 激活方式

| 机制          | 激活方式     | 具体说明                                       |
| :------------ | :----------- | :--------------------------------------------- |
| **Rules**     | **始终激活** | 只要在面板中启用，每次对话都会加载到系统提示   |
| **Skills**    | **按需触发** | Cline 根据你的请求描述判断是否需要加载完整内容 |
| **Workflows** | **手动调用** | 需要输入 `/workflow-name` 斜杠命令才执行       |
| **Hooks**     | **自动触发** | 监听特定事件（如文件保存、命令执行）自动运行   |

### 2️⃣ Token 消耗

| 机制          | Token 消耗         | 优化策略                                          |
| :------------ | :----------------- | :------------------------------------------------ |
| **Rules**     | **每次对话都消耗** | 建议保持精简，避免过多规则拉长上下文              |
| **Skills**    | **渐进加载**       | 元数据常驻（~100 tokens/Skill），完整内容按需加载 |
| **Workflows** | **执行时消耗**     | 只有调用时才加载工作流定义内容                    |
| **Hooks**     | **触发时消耗**     | 仅在事件发生时执行，不占用对话上下文              |

### 3️⃣ 内容复杂度

| 机制          | 适合内容量 | 典型长度                         |
| :------------ | :--------- | :------------------------------- |
| **Rules**     | 简短到中等 | 几十到几百行，几条到几十条规范   |
| **Skills**    | 中等到大量 | 几百到几千行，可包含子文档、脚本 |
| **Workflows** | 中等       | 几十到几百行，通常是一个具体流程 |
| **Hooks**     | 简短       | 通常几十行代码，逻辑明确         |

### 4️⃣ 文件存储

| 机制          | 存储位置                                                 | 文件格式                              |
| :------------ | :------------------------------------------------------- | :------------------------------------ |
| **Rules**     | 全局：`~/Documents/Cline/Rules/`<br>项目：`.clinerules/` | 单个 `.md` 文件，支持 YAML 前置元数据 |
| **Skills**    | 全局：`~/.cline/skills/`<br>项目：`.cline/skills/`       | 文件夹结构，含 `SKILL.md` + 可选资源  |
| **Workflows** | 项目：`.cline/workflows/`                                | 单个 `.md` 文件，支持 YAML 元数据     |
| **Hooks**     | 项目：`.cline/hooks/`                                    | 脚本文件（`.sh`、`.py`、`.js` 等）    |

## 🎨 使用场景对比

### Rules 适用场景

- ✅ 设定代码风格（缩进、引号、命名）
- ✅ 项目架构约束（目录结构、模块划分）
- ✅ 安全规范（禁止硬编码密钥、SQL 注入防范）
- ✅ 团队协作标准（commit 格式、PR 模板）

### Skills 适用场景

- ✅ 框架深度知识（React、Vue、Django 最佳实践）
- ✅ 特定领域工作流（数据分析、机器学习、数据库设计）
- ✅ 第三方集成规范（AWS、Stripe、OpenAI API 调用）
- ✅ 可复用的专家知识库（公司内部技术栈经验）

### Workflows 适用场景

- ✅ 发布流程（版本号更新 → 运行测试 → 构建 → 部署）
- ✅ 代码审查流程（检查规范 → 运行 lint → 生成报告）
- ✅ 数据库迁移（备份 → 执行迁移 → 验证 → 回滚预案）
- ✅ 文档生成（提取注释 → 生成 API 文档 → 更新站点）

### Hooks 适用场景

- ✅ 自动化质量检查（保存前运行 lint、测试）
- ✅ 操作日志记录（记录文件修改、命令执行）
- ✅ 外部通知（部署成功后发送 Slack 消息）
- ✅ 资源清理（任务完成后清理临时文件）

## 💡 组合使用示例

这四个机制不是孤立的，可以**协同工作**。让我用一个完整的发布场景来展示：

### 场景：发布一个新版本到生产环境

```
┌─────────────────────────────────────────────────────┐
│  开发者：输入 /release v2.0.0                       │
└─────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────┐
│  Workflow: release.md                               │
│  ├─ 步骤1：读取 Rules 中的版本规范                  │
│  │    - 必须使用语义化版本（Rules）                  │
│  │    - CHANGELOG 格式必须符合规范（Rules）          │
│  ├─ 步骤2：加载 Skills 中的部署知识                 │
│  │    - AWS 部署最佳实践（Skills）                   │
│  │    - 蓝绿部署策略（Skills）                       │
│  ├─ 步骤3：执行具体操作                             │
│  │    - 更新版本号                                   │
│  │    - 运行测试套件                                 │
│  │    - 构建生产包                                   │
│  │    - 部署到服务器                                 │
│  └─ 步骤4：触发 Hooks                               │
│       - 部署成功后发送通知（Hook）                   │
│       - 记录部署日志（Hook）                         │
└─────────────────────────────────────────────────────┘
```

### 具体代码示例

**Rules（约束规范）**

```markdown
---
paths: ["package.json", "CHANGELOG.md"]
---

# 版本发布规范

1. 版本号必须遵循 semver 规范（major.minor.patch）
2. CHANGELOG 必须包含 Added/Changed/Fixed 三类内容
3. 发布前必须通过所有测试
```

**Skills（专家知识）**

```markdown
---
name: aws-deployment
description: AWS deployment best practices and configuration
---

# AWS 部署指南

## 蓝绿部署策略

- 保留两个独立环境（Blue 当前生产，Green 新版本）
- 验证 Green 环境健康后再切换流量
- 保留回滚能力至少 30 分钟
```

**Workflow（执行流程）**

```markdown
---
name: release
description: Full release workflow
---

# 发布流程

1. 读取 Rules 中的版本规范
2. 询问用户确认版本号
3. 运行 `npm run test` 确保测试通过
4. 根据 Skills 中的部署策略执行部署
5. 触发 post-deploy hooks
```

**Hook（自动化触发）**

```bash
#!/bin/bash
# .cline/hooks/post-deploy.sh

# 发送部署成功通知到 Slack
curl -X POST -H 'Content-type: application/json' \
  --data '{"text":"✅ 部署成功！版本：'$VERSION'"}' \
  $SLACK_WEBHOOK_URL
```

## 🎓 最佳实践建议

### 1. 内容分层策略

```
Rules     → 存放"什么不能做"（禁止项、约束）
Skills    → 存放"应该怎么做"（最佳实践、指南）
Workflows → 存放"步骤是什么"（流程、脚本）
Hooks     → 存放"自动做什么"（触发式操作）
```

### 2. 命名规范建议

```
Rules:     coding-standards.md, security-rules.md
Skills:    react-best-practices/, aws-deployment/
Workflows: release.md, code-review.md
Hooks:     pre-commit.sh, post-deploy.py
```

### 3. 性能优化

- **Rules**: 保持精简，合并相似规则
- **Skills**: 利用渐进加载，描述字段要精准
- **Workflows**: 避免过于复杂的嵌套逻辑
- **Hooks**: 确保快速执行，避免阻塞主流程
